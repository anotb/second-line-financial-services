# Gold-standard review vs Anthropic's pattern

Date: 2026-05-06
Author: independent reviewer (subagent)
Subject: `scoping/SKILL.md` as the template for batch 2D-1
Context: 46 of ~68 skills built; 22 to go; the orchestrator wants an outside read before locking the pattern in.

## 1. Top-line judgment

The gold-standard reads well. As a piece of practitioner prose it lands; the voice is the voice you want, the workflow is the work a senior reviewer actually does, and the seams between draft and sign-off are honest. As a *companion* to `anthropics/financial-services` it diverges in shape more than the framing suggests, and that divergence is mostly the right call but worth being honest about.

Anthropic's skills are flat. `comps-analysis` is a single 660-line `SKILL.md`. `dcf-model` is a 1,260-line `SKILL.md` plus a TROUBLESHOOTING, a `requirements.txt`, and a `scripts/` folder. No `references/`, no `templates/`, no `schemas/`, no `examples/`. They put everything inline, including hex codes, formula strings, openpyxl examples, and "ALWAYS ask yourself first" prompts. The structure is "one big skill file plus the code it shells out to". The second-line repo has chosen a more decomposed layout: SKILL.md + references/ + templates/ + (sometimes) schemas/ + examples/ + TROUBLESHOOTING.md. That is a real difference in philosophy, not a stylistic one. It happens to be defensible because second-line work is regulator-driven and citations move; spreadsheet conventions don't. But the orchestrator should stop describing this as "the same pattern Anthropic uses". It isn't.

The companion-repo positioning is fine if the README and the agent-plugin shape mirror Anthropic's pitch-agent / managed-agent-cookbook split. From the directory listing it looks like that exists (six standalone agent plugins, capability bundles). If the agent.yaml-equivalent for the second-line agents follows Anthropic's manifest shape, the family resemblance holds where it actually matters.

## 2. Structural comparison

**File set per skill.** Anthropic: SKILL.md (often huge), occasional TROUBLESHOOTING, scripts when there's executable code, requirements.txt. That's it. Second-line: a six-folder layout. The decomposition is principled if and only if (a) the references files load conditionally and (b) practitioners actually consume `templates/default-output.md` as the renderer's input. The orchestrator's "load only what the scope flags" rule makes the references split coherent. The templates split is also coherent because the deliverable is rendered by `docx`/`xlsx`/`pptx` and the template is the content spec for those skills. The `examples/` split is the weakest of the three; Anthropic puts examples in the body or in a separate file referenced from the body, and the second-line `examples/` folder exists more because the skeleton template says it should than because something downstream needs it.

**Naming.** Both repos use kebab-case skill slugs. Both bury skills under `plugins/<type>/<plugin>/skills/<skill>/`. No issue.

**Frontmatter.** Anthropic's frontmatter is a single `description` string with markdown formatting inside it (Perfect for / Not ideal for / a paragraph). Second-line's frontmatter uses a YAML block-scalar with the same shape (Best for / Not the right tool when) plus an `argument-hint`. Functionally identical. The "drop Anchored to" decision is sound; it would have polluted activation context with regs that don't apply to the engagement. The `argument-hint` field is useful and Anthropic doesn't have one; if it's a Claude Code extension, fine.

**Body shape.** Anthropic opens with a blunt, often shouty section ("⚠️ CRITICAL", "ALWAYS ask yourself first", "DO use / DO NOT use"). The body proceeds in numbered sections that mix prose, tables, code blocks, and inline rules. Second-line opens with a soft framing paragraph, an "Ask first" bullet block, and a long prose section called "How the charter gets built". Both work. Anthropic's is louder; second-line's is closer to the voice of a memo from a partner. The second-line pattern is the right voice for the audience (CRO, head of model risk, head of regulatory affairs read memos, not workflow gauntlets).

**Output handoff.** Anthropic's `dcf-model` says the deliverable is an Excel model and tells Claude how to build it directly with openpyxl or Office JS. Anthropic's `pitch-agent` orchestrates child skills (`pitch-deck`, `comps-analysis`, `dcf-model`) and lets each emit its own artifact. Second-line says "render via the `docx` skill in the `document-skills` plugin". That's a *cross-plugin* dependency. Anthropic's pattern is *within-repo* — the rendering skills (`pptx-author`, `xlsx-author`) ship in the same plugin family. The second-line choice to externalize rendering to Anthropic's `document-skills` plugin is sensible (don't reinvent docx generation) but it is a real install-time dependency that should be documented in every plugin README and probably enforced in the plugin manifest. The skeleton template names this; whether the plugin manifests actually declare it is worth a check.

## 3. Voice and prescription level

Anthropic's two skills sit at opposite ends. `comps-analysis` is judgement-shaped: "Adapt based on specifics", "User-provided examples and explicit preferences always take precedence over defaults", a "Core philosophy" line ("Build the right structure first, then let the data tell the story"). `dcf-model` is structured-artifact: numbered Steps 1-N, formula recipes, "NON-NEGOTIABLE" callouts, sensitivity-table dimensions specified to the cell. That divergence inside the same plugin is interesting. They picked the prescription level the work demanded.

`scoping` sits closer to `comps-analysis` than to `dcf-model`. That is the right place for *that particular skill* — engagement scoping is judgement work; you cannot prescribe how a CRO sets the boundaries of a regulatory-change engagement. But the orchestrator is treating `scoping` as the template for *all twelve* skills in batch 2D-1, and that worries me. Some of those skills (looking at the built ones: `dora-register-builder`, `model-card-builder`, `control-matrix`) are closer to `dcf-model` in character — there *is* a structure-bearing artifact with named sections, mappings to ITS tables, tier-driven depth gates. If batch 2D-1 includes anything in that register-shaped family, applying the judgement-shaped voice to it will make the artifact mushy.

The orchestrator should pick the voice per skill. The skeleton template is fine as a default; the build contract should explicitly say "match the prescription level to the work, not to the template — `dora-register-builder` is closer to `dcf-model`, `scoping` is closer to `comps-analysis`".

## 4. The "delegate to docx/xlsx/pptx" pattern

Clean enough. Two notes.

First, Anthropic's `pitch-agent` calls `pitch-deck`, `xlsx-author`, `pptx-author` — but those *ship in the same repo*. They are first-party. The second-line repo is delegating to Anthropic's separately-shipped `document-skills` plugin. That's a different operational story. If a firm installs `risk-compliance-core` without `document-skills`, every output skill breaks silently (or with a confusing error). The plugin manifest needs a hard `requires:` on `document-skills`, and the README needs to say it loud. CLAUDE.md says "edit existing files", but no one has checked whether every plugin.json declares this dependency.

Second, the framing "the deliverable is a Word memo, render via `docx`" is correct for memos. It is wrong for some artifacts. `dora-register-builder` is xlsx-shaped (it's a tabular register). `risk-committee-pack` is pptx-shaped. The skeleton template handles this with a placeholder, but the gold-standard reads as if Word is the default. For the orchestrator: the build contract should explicitly say "pick the format per artifact, the default is *not* Word".

Third edge case: some artifacts are genuinely both. A model card has narrative (memo) and a tier matrix (table). The cleaner pattern is one primary deliverable plus a structured record (the JSON) that downstream skills consume — which is what `scoping` already does. That pattern generalizes; the skeleton template should call it out. Right now it's implicit.

## 5. References-first design

About right, with one wobble.

The argument is solid: regulators get re-issued, citations move, firms install their own overlays, and a SKILL.md that hardcodes "SR 11-7 §V" is brittle. Putting the named regulator, dated, with section refs into `references/source-anchors.md` and letting SKILL.md talk about "the named regulatory anchors" is the right move for a repo that wants firm overlay and regulator drift handled cleanly.

The wobble: Anthropic's `dcf-model` puts substantive *technical* content inline (formulas, hex codes, openpyxl examples). Nobody would argue those should be in `references/openpyxl-conventions.md`. Why? Because the technical conventions don't drift with regulator action, they don't differ by jurisdiction, and the firm doesn't overlay them. The references-first cut works for *regulatory* content; it would not work for *technical* content. The second-line repo doesn't have technical content of the dcf-model variety, so the cut works uniformly. Worth flagging anyway: if a future skill ships executable code (a sampling-plan generator, a HMDA-test workpaper builder), the same references-first instinct would push the code into `references/` where it does not belong. The rule needs to be "regulatory citations live in references; technical conventions live where the work lives".

The other concern: by stripping all regulator names from the body, the skill loses some signal that helps Claude pick the right anchor file at runtime. `scoping`'s body says "the named regulatory anchors" three times. Claude has to know to load `references/source-anchors.md` to find out who they are. If the scope record carries the regulator list (it does, via `institution.primary_regulators`), that's fine — Claude reads scope, loads matching reference. If scope is absent or partial, Claude is one indirection further away from the citations than it would have been with regulators named in the body. The orchestrator's bet is that the conditional-load discipline outweighs the indirection cost. I think that's right for this repo, but the build contract should test it: pick three skills, run them with no scope, see whether Claude picks up the right anchors.

## 6. Schemas-optional

Reads right. Anthropic doesn't ship JSON Schemas at all in the skills I looked at — the structure is implicit in how they tell you to build the spreadsheet. The second-line decision to keep schemas only where downstream automation genuinely needs them (scope record consumed cross-skill, DORA register row that maps to EBA ITS, sanctions alert payload) is honest. The over-schema'd v1 was the kind of thing that happens when an engineer designs a knowledge-work repo. Stripping it back to "schema only when there's a downstream consumer that needs the structure" is right.

The risk: subagents will default to writing schemas because schemas are "professional" and the skeleton has an `OPTIONAL` slot for them. The build contract should be more aggressive: "default to no schema. If you write one, justify it in the spec sheet. The reviewer will challenge every schema." Otherwise you'll get 12 schemas in batch 2D-1 with three that are useful and nine that are decoration.

## 7. What I would change

Five concrete changes.

**1. Per-skill voice calibration in the build contract.** The build contract should say explicitly: "Pick judgement-shaped (`comps-analysis`-style) or structured-artifact (`dcf-model`-style) per skill before drafting. Register builders, matrices, and tier-driven cards are `dcf-model`-shaped. Charters, intake forms, scoping memos, and judgement reviews are `comps-analysis`-shaped. Not every skill in batch 2D-1 inherits `scoping`'s prose-heavy voice."

**2. Make the `document-skills` dependency explicit in plugin manifests.** Walk every plugin.json and add `requires: ["document-skills"]` (or whatever the plugin manifest format supports). Add a one-line install-order note to every plugin README. Right now it's a soft footnote and a firm that installs only the second-line plugins will find skills that emit nothing.

**3. Aggressive default-to-no-schema posture.** Rewrite the schema clause in the build contract from "OPTIONAL: only if the artifact has a structure that genuinely helps downstream automation" to "DO NOT WRITE A SCHEMA. If you believe one is genuinely needed, name the downstream consumer skill that reads it. The reviewer will challenge every schema and most will be rejected." Default-on flips human nature in the wrong direction.

**4. Drop `examples/` as a default folder; use it where the skill earns it.** Anthropic doesn't ship `examples/` per skill. The second-line `examples/` folder exists because the skeleton says it should, not because anything downstream consumes it. For judgement-shaped skills (scoping, AI use-case intake), one or two worked examples are useful. For mechanical skills (control-matrix, DORA register), examples bloat the file count and add nothing. The build contract should say "include `examples/` only when the skill's output has a distinctive shape that an analyst couldn't infer from the template". That is maybe half the skills, not all of them.

**5. Add a "what context does this skill load at runtime" section to the build contract.** The references-first design only works if Claude knows what to load and when. The skeleton implies it ("the scope flags banking, load `references/sector-overlays/banking.md`") but no skill currently has a budget for "this is what loads conditionally and this is what loads always". For a 22-skill batch where every skill is going to add 1-4 reference files, a runtime context budget per skill is overdue. Otherwise you ship 22 skills that each load 6 reference files at activation and Claude is reading 130 files before it does any work.

## 8. What concerns me about scaling to 22 more skills

Three things worth watching in the agent reports.

**Voice drift.** The orchestrator just spent a session sharpening `scoping` and producing the anti-AI-tells memory. Every subagent is going to read those memories, internalize the rules, and write skills that *quote the memory back at themselves*. You'll see SKILL.md files that anxiously avoid every banned word and end up sounding scrubbed rather than confident. Watch for: skills where every paragraph is one sentence (overcorrection on "fewer headers, more prose"); skills where the workflow narrative refuses to give numbered steps even when the work is genuinely sequential; skills where the body avoids saying anything load-bearing because the memory said "drop the load-bearing section". The fix is in review: read the prose for *confidence*, not for rule compliance. A skill that sounds like a senior practitioner sometimes says "this is non-negotiable" because some things actually are.

**The references folder bloating.** 12 skills × (source-anchors + 4 sector overlays + 4 cross-cutting + firm overlay) is potentially 108 reference files for batch 2D-1 alone. Most of those should not exist. The build contract says "files only when needed" but subagents under watchdog pressure will create stub files because the skeleton has slots for them. Watch for: empty or near-empty sector overlay files; sector overlay files that just restate the source-anchors content; cross-cutting overlays for cyber/privacy/climate/conduct on every skill regardless of whether the skill has cross-cutting nuance. If a sector overlay file is shorter than the workflow paragraph that references it, kill it.

**Schemas creeping back in.** Even with the no-schema-default posture, three or four subagents will write schemas because the skill name suggests structure (anything ending in `-register`, `-matrix`, `-pack`, `-binder`). Some of those are right (`dora-register-builder` does need a schema; the EBA ITS mapping is the canonical case). Most will be over-engineering. Per skill, ask: who reads this schema? If the answer is "no other skill in the repo", reject it.

**The duplicate-content check.** Rule 4 in the validator catches >50% overlap. With 12 skills sharing the same skeleton and the same scope-integration paragraph and the same "render via docx" output handoff, the boilerplate is going to push close to that line. Either accept that the boilerplate is shared on purpose (and lower the threshold to maybe 70% for sections that are genuinely shared scaffolding), or extract the boilerplate into a referenced doc that SKILL.md links to. The current setup will either flag legitimate skills as duplicates, or the validator's threshold is implicitly assuming subagents will paraphrase the boilerplate just enough to dodge the check, which is the worst of both worlds.

**One thing that surprised me.** The gold-standard `scoping/SKILL.md` puts the structured-record decision (the JSON schema is canonical and consumed by every other skill) in the very last paragraph of the Output section. For the file that is the *cross-skill contract for the whole repo*, that is buried. A practitioner reading the skill would think the deliverable is the Word charter and the JSON is a side artifact. From a downstream-consumer perspective the JSON is the load-bearing output and the Word charter is the human-facing wrapper. I would invert the framing: lead Output with "the structured record is the contract every other second-line skill consumes; the Word charter is the human artifact the sponsor signs". That is a small voice change but it tells subagents reading this as the template that the structured record matters when it's the actual cross-skill seam.
